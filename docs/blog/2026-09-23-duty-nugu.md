# 엑셀 속 당직표가 “당직 누구?”가 된 하루

_2026년 9월 23일 · 당직 누구? 제작 일지_

![당직 누구? 서비스 목업](../readme-preview.png)

오늘의 출발점은 단순했다. **“오늘 누가 당직이지?”** 매달 올라오는 엑셀 명단에는 답이 있지만, 답을 찾을 때마다 파일을 열고 시트를 훑어야 했다. 그 반복을 줄이려고 부산광역시 동구 당직 명단을 검색 가능한 웹 화면으로 옮겼다. 밤이 되자 화면은 오늘의 당직, 월별 일정, 이름별 이력과 통계를 함께 보여주고 있었다.

## 오후 — 엑셀을 웹 화면으로 옮기다

프로젝트를 세팅하고, 명단을 읽는 전처리 스크립트와 정적 웹앱을 만들었다. 데이터 흐름은 단순하게 유지했다.

```text
엑셀 명단(.xls/.xlsx) → scripts/preprocess.py → app/data.js → 브라우저 화면
```

[전처리 스크립트](../../scripts/preprocess.py)는 `pandas`로 명단의 날짜·구분·직책·부서·이름을 정리하고, 브라우저에서 읽을 수 있는 `DUTY_DATA`를 만든다. 앱 자체는 서버 API 없이 정적 파일로 실행된다. 덕분에 사용자는 설치 과정 없이 [GitHub Pages](https://hanjjaem.github.io/danjik-nugu/)에서 바로 열 수 있다. 휴대폰 화면은 별도 미리보기에서 먼저 다듬은 뒤 실제 앱에 반영했다. 좁은 화면에서도 검색창과 일곱 칸짜리 캘린더가 함께 버텨야 했기 때문이다.

## 저녁 — “보이는 속도”와 “입력되는 속도”

캘린더를 손보는 일은 색을 고르는 것으로 시작했다. 헤더 회색을 짙게 하고, 일요일에는 옅은 빨강, 토요일에는 옅은 파랑을 입혔다. 세로 구분선도 더해 날짜를 읽기 쉽게 했다. 다만 검색된 날짜와 가장 최근 당직일이 주말 색에 묻히면 안 된다. [스타일시트](../../app/style.css)에서 일반 주말 셀에만 색을 적용하고, 검색 강조 셀의 스타일이 우선하도록 선택자를 조정했다.

그다음에는 월 넘김과 이름 입력이 답답하게 느껴졌다. 처음에는 달력 문자열을 캐시하고 화면 교체를 다음 프레임으로 미뤘지만, 체감상 충분하지 않았다. 최종적으로 [앱 코드](../../app/app.js)는 **월·검색 이름·강조 날짜**를 키로 삼아 캘린더 DOM 노드를 최대 세 개 보관한다. 같은 달로 돌아오면 노드를 재사용하고, 달력이 바뀔 때는 `replaceChildren()`로 교체한다. 일정별 툴팁 이벤트도 각각 붙이지 않고 캘린더 루트에서 처리한다. 전환 애니메이션을 덜어내니 조작과 화면 변화가 더 가깝게 느껴졌다.

검색창 쪽은 한글 조합 입력이 핵심이었다. 입력 중간값으로 화면 전체를 계속 다시 그리면 글자가 끊겨 보일 수 있다. `compositionend`에서 완성된 입력을 처리하고, 직전과 같은 이름이면 작업을 건너뛰도록 했다. 통계 표 역시 검색할 때마다 통째로 만들지 않고 해당 이름의 행에 강조 클래스만 바꾼다. Enter를 누르면 키보드를 닫고 개인 이력 영역으로 이동한다.

> **성능 메모:** DOM 재생성과 불필요한 표 갱신을 줄인 것은 코드에서 확인된다. 다만 전후 프레임 시간이나 입력 지연을 수치로 측정한 기록은 없다. 이번 결론은 구현 변경과 사용 중 느낀 차이에 근거한다.

## 밤 — 한 글자의 색과 그림자를 오래 바라보다

히어로의 **“당직 누구?”**는 핫핑크에서 보라색으로 흐르는 그라데이션이다. 배경이 화려한 만큼 글자 가장자리가 쉽게 묻혔다. 흰색 테두리처럼 보이게 하려고 `background-clip: text`와 여러 겹의 `drop-shadow()`를 조합했다. 작은 흰 그림자들이 밝은 버퍼를 만들고, 뒤의 어두운 그림자가 배경에서 글자를 떼어 준다. 그림자를 크게만 키우면 획 사이가 번져 보였기에 작은 흰 그림자와 넓은 어두운 그림자의 역할을 나눴다.

크기를 직접 바꿀 때 볼 값도 분명해졌다. 데스크톱의 제목 크기는 `font-size: clamp(60px, calc(3.7vw + 10px), 100px)`, 모바일은 별도의 `clamp(48px, calc(4vw + 35px), 62px)`가 적용된다. 데스크톱 선언만 바꿨는데 휴대폰에서 그대로라면 아래쪽 미디어 쿼리가 덮어쓰고 있는지 확인해야 한다.

## 마무리 — 기능을 설명하는 대신, 흐름을 보여주다

기술 설명으로 가득했던 README는 **“오늘 누가 당직이지? 내 차례는 언제지?”**라는 사용자 질문에서 다시 시작했다. HTML로 제품 목업을 만들고 PNG로 렌더링했다. 이어 실제 앱에서 `한재림`을 검색하는 흐름을 Playwright로 캡처하고 Pillow로 13초 GIF를 만들었다. 검색 → 캘린더 강조 → 당직 횟수와 월별 그래프 → 이력 → 전체 통계의 선택된 행까지 한 번에 볼 수 있다.

![한재림 검색부터 당직 이력과 통계까지 이어지는 실제 앱 시연](../readme-demo.gif)

GIF 생성 코드는 [build-readme-demo.py](../build-readme-demo.py)에 남겼다. 캡처 도중 최근 당직일 강조, 이력, 통계 표의 선택 행이 실제로 존재하는지도 확인한다. 목업은 설명용 예시이고, GIF는 당시 앱 화면을 녹화한 기록이다.

## 다음에 다시 열어 볼 메모

- **성능:** 월 이동과 검색 입력을 브라우저 Performance 도구로 측정해 체감과 수치를 함께 남기기.
- **CSS:** 여러 차례의 시각 조정으로 쌓인 캘린더·모바일 선택자를 정리해 최종 스타일의 위치를 찾기 쉽게 만들기.
- **문서 구조와 데이터:** 현재 히어로 제목 요소의 의미를 점검하고, `app/data.js`가 공개 저장소와 Pages에 포함된다는 점을 명단 갱신 때마다 확인하기.

돌아보면 오늘 가장 오래 붙잡은 것은 거대한 기능이 아니었다. 달력이 한 박자 늦게 움직이는 느낌, 한글 이름이 매끄럽게 써지는지, 제목의 흰 빛이 어디까지 번져야 하는지 같은 작은 차이였다. **찾는 시간을 줄이는 도구는, 사용하는 순간의 작은 기다림부터 줄여야 한다.**
